# M03 — Deploy em Beta (Docker Swarm)

## Estado

**Aberto em 2026-09-28**, por decisão de Marcio, através da entrevista de
roadmap pós-M02. O M02 foi fechado em 2026-09-15 e não é reaberto por este
marco: trabalho novo entra inteiramente por aqui.

## Objetivo

Colocar o sistema (backend FastAPI, frontend Next.js, worker Procrastinate,
Postgres e Qdrant) rodando em produção via Docker Swarm, em um VPS já
disponível, acessível por domínio próprio com HTTPS, para uso interno da
equipe de consultoria, com backup automático do banco de dados.

Origem: pedido explícito de Marcio em 2026-09-28 para focar nos itens que
levam o sistema a rodar em Beta, depois de SPEC-0021 (chat com assistente) ter
sido entregue e mesclada em `main`. Nenhum marco anterior (M01, M02) cobriu
infraestrutura, deploy, domínio, secrets de produção ou backup — o sistema
sempre rodou só localmente (`next dev` + backend FastAPI local + Postgres de
teste via Docker Compose), e o `$specsfy-setup` deliberadamente adiou
Dockerfile, versionamento e deploy até um pedido explícito.

## Condição de saída

1. Dockerfiles de produção para backend, frontend e worker, e stack file do
   Swarm cobrindo todos os serviços, incluindo Postgres e Qdrant de produção
   distintos dos recursos de teste (`BACKLOG-0028`).
2. Domínio apontado com HTTPS válido, por reverse proxy com certificado
   emitido automaticamente (`BACKLOG-0029`).
3. Secrets de produção (OpenRouter, Cloudflare R2, banco, sessão) geridos por
   `docker secrets`, nunca em texto puro no stack file nem versionados
   (`BACKLOG-0030`).
4. Backup automático diário do Postgres de produção, com retenção definida
   (`BACKLOG-0031`).
5. Runbook documentado do processo de deploy manual (`BACKLOG-0032`).
6. Owner/admin consegue logar, criar Pessoas, subir uma Base e conversar com o
   assistente no ambiente de produção, com Ruff, Pytest e build do frontend
   verdes antes de cada deploy.

## Dependências

Nenhuma bloqueante externa a este marco. Toda a camada de aplicação já está
implementada e mesclada em `main` (SPEC-0012, SPEC-0019, SPEC-0020,
SPEC-0021); falta somente a camada de infraestrutura e deploy.

## Hipóteses dependentes de uso real

Não são requisito, apenas registro de risco:

- O volume de uso interno inicial (Marcio e equipe de consultoria) cabe em um
  único VPS/nó Swarm, sem necessidade de ajuste de capacidade ou de múltiplos
  nós nesta fase.
- Um snapshot diário simples de backup é suficiente para o risco aceito nesta
  fase; uma estratégia mais robusta (point-in-time recovery, réplica) pode se
  mostrar necessária com o uso real.

## Fora de escopo

- Deploy automático via CI/CD — decidido por Marcio em 2026-09-28: o deploy
  desta fase é manual; automação fica para um marco futuro.
- Cadastro aberto ou Beta público — o uso nesta fase é interno (Marcio e
  equipe de consultoria); gestão de Pessoas continua pelo owner/admin
  existente, sem mudança de fluxo de autenticação.
- Autoscaling ou cluster Swarm com múltiplos nós — nesta fase, um único VPS já
  disponível é suficiente.
- Observabilidade avançada (métricas, tracing distribuído) — mesmo limite já
  declarado em `PROJECT.md` para o projeto-mãe; fora de escopo deste marco.
- Migração de Postgres ou Qdrant para serviços gerenciados externos — ambos
  rodam como serviços do próprio Swarm nesta fase.
